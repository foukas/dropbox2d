## Problem Statement

The seesaw bare mechanic shipped on 2026-10-06. It is a revolute-jointed plank beside the row's gap that tips under the ball. The user's verdict after playing it: "I'm not seeing the seesaw value as it is now. It just tilts due to the ball's weight/gravity and does nothing else." The planned follow-up was an angular-velocity-driven ball launch (old doc Approach C). This session ruled it out for two reasons:

- **It's either redundant or scripted.** A passive seesaw driven only by the ball can't return more energy than the ball put in. Box2D contact already transfers the plank's surface velocity to the ball. So an explicit launch either duplicates existing physics or injects energy, which is a scripted boost that breaks the "pure physics" rule.
- **It points the wrong way.** In the user's words: "Flinging the ball in a direction that is not down is impeding the goal too much I think."

So the problem isn't "make the seesaw launch." It's that the seesaw doesn't change any decision in a game about going down.

## What Makes This Cool

- **In a game about going down, a seesaw should be a door.** Platformer seesaws exist to reach higher ground, the wrong direction for this game. The real-world forms that fit a descent game are the weight-triggered trapdoor and the bascule drawbridge. The FallDown genre is about choosing which hole to go for.
- **The trapdoor makes your own weight create a second way down.** The plank spans a hole in the row and rests level. Land off-center and it swings open under you, and you drop through a door you opened yourself.
- **It's the skilled route.** It keeps your combo and saves the trip to the guaranteed gap.
- **It's still real physics.** No motor, no scripted velocity. The door rights itself through a keel weight hung below the pivot, the way a ship does.

## Symbols

| Symbol | Meaning | Value / range |
|---|---|---|
| W | hole width (lip corner to lip corner) | swept 2.3–2.7 |
| L | plank half-length | W/2 + 0.1 (the plank overlaps each lip by 0.1) |
| t | platform/plank thickness | `PLATFORM_THICKNESS` = 0.35 (half = 0.175) |
| θmax | joint limit (both directions) | swept 70°–85° |
| θ_pass(W) | minimum tilt at which clearance(W) ≥ d_ball + margin, i.e. the door actually passes the ball | from the clearance table below. A sweep cell is feasible only if θmax ≥ θ_pass + 5° |
| M | keel mass (added to the plank body's mass) | swept {0.1, 0.2, 0.3} |
| k | keel center distance below the pivot | swept {0.3, 0.6, 1.0} |
| ω-damp | plank angular damping | swept {0.5, 1.5, 3.0} |
| d_ball | ball diameter | 0.8 (`BALL_RADIUS` 0.4) |
| margin | clearance safety margin | 0.1 |
| minFiller | minimum wall filler width | `MIN_FILLER_WIDTH` = 0.3 |
| minLip | minimum gap-side lip width | 0.3 (new constant, same posture as minFiller) |

The shipped seesaw's `SEESAW_HALF_LENGTH = 0.9` is the plank half-length, so a hole it could span would be at most W ≈ 1.6. That fails the clearance at every angle (see below). The constant's meaning changes for the trapdoor, not just its value.

## Constraints

- **Pure physics, no exceptions.**
  - No joint motor, no `setLinearVelocity`/impulse on the ball, no scripted closing.
  - Self-righting comes only from mass placement: a keel moment `M·k` below the pivot.
  - Tilt steering stays live on the plank, so the player can lean the ball to work the door. That is emergent, and needs no new code.
- **Geometry must pass a 0.8-diameter ball, with plank thickness included.** The cross-model pass corrected the session's first estimate, which ignored thickness. The clearance check, using the lip-corner-to-tilted-plank distance minus both half-thicknesses (0.175 each), is:

  `(W/2)·sinθ − 0.175·cosθ − 0.175 ≥ 0.8 + margin`

  - A hole the shipped plank could span (W ≤ ~1.6) fails even at 90°: 0.8 − 0.175 = 0.625 < 0.9.
  - Minimum W with margin, worked through the formula:

    | θ_pass | Minimum W |
    |---|---|
    | 60° | ≈ 2.68 |
    | 70° | ≈ 2.44 |
    | 75° | ≈ 2.32 |
    | 80° | ≈ 2.24 |
    | 85° | ≈ 2.19 |

  - **Committed range:** W ∈ {2.3, 2.5, 2.7} with θmax swept over 70°–85°. W = 2.7 passes from about 60°, so it tolerates a door that never swings fully open. W = 2.3 needs θmax ≥ ~81° (θ_pass ≈ 76° + 5°).
    - Cells where θmax < θ_pass + 5° (W = 2.3 with θmax 70°, 75° or 80°) stay in the grid as **expected-fail controls**. They must classify as not-passed, which proves the test can see a too-small hole.
  - **Per-side span requirement:** minFiller + W + minLip = 2.9–3.3 units.
  - The hole is about the size of `GAP_MIN_WIDTH` (2.4). **It will read as a second gap with a lid, and that's accepted.**
- **Keel bound: the top failure mode is a door that's too heavy and wedges.**
  - With the ball at the plank end, the door settles where `tanθ = m_ball·L / (M·k)`. Ball mass is ~0.503.
  - If `M·k` is too large, the door settles short of the clearance angle. The ball wedges between the plank tip and the lip corner and stops descending. Rows are static bodies in world space and only the camera scrolls down, so a ball that stops descending leaves the top of the view and the run ends. That's the worst bug this game can have.
  - Because rows never move, a static-row test reproduces this failure exactly. "Wedged" just means "stopped descending."
  - Design rule: `M·k < m_ball·L / tan(θ_pass)`, verified empirically (see Next Steps), not just statically.
- **Impact dominates static balance.**
  - An ~11 m/s landing slams a ~0.4 kg plank to its limit, and the ball bounces (ball restitution 0.55). Self-righting can close the door before the ball comes back down.
  - Opening and closing timing matters more than the equilibrium math. Box2D combines restitution as the max, so lowering bounce on the plank needs a `preSolve` contact override (`contact.setRestitution()`).
  - That override is a planned sweep dimension (as-is vs. 0.1). **Adoption rule:** it ships only if no as-is combination meets every acceptance threshold. It is still physics (a material property), not scripting.
- **Keel method (decided): `Body.setMassData()`, no keel fixture.**
  - Once its single plank fixture exists, the factory sets the plank body's mass data:
    - mass = plank fixture mass + M;
    - center = (0, −M·k / total mass) in body coordinates;
    - rotational inertia I = the plank's own inertia about the pivot + M·k².
  - **Ordering rule:** `setMassData` must be the last mass-affecting call. Box2D's `resetMassData()` (run by any later `createFixture`) would wipe it.
  - Why this method:
    - There's no second fixture, so the renderer's `getFixtureList().get(0)` and the tag checks are unaffected.
    - Nothing can collide with it.
    - It's a pure physics parameter.
  - `TrapdoorFactory` builds it identically for the game and the test, so the sweep measures the exact inertia that ships.
  - The plank (L ≈ 1.25–1.45) hanging at θmax reaches about −1.4 below the row, well above the next row's top surface at about −2.425.
- **Settling (decided): plank angular damping is allowed.**
  - A keeled plank on a frictionless revolute joint is an undamped pendulum; it would swing through level indefinitely. `Body.setAngularDamping()` is a body physics parameter in the same category as the biomes' ball `linearDamping`, not a motor or a scripted correction.
  - Its value is a sweep dimension.
  - Settle criterion: within 1.5 s of the ball passing, |θ| < 5° and stays there.
- **Both lips join the reserved no-collide group.**
  - The plank overlaps both lips slightly (2L a little more than W) so it covers the hole at rest.
  - Both the wall filler and the new gap-side lip must be in `SEESAW_NO_COLLIDE_GROUP`, or the plank jams on its first rotation. Today only the wall filler gets the group.
  - The reserved-constant rule from the old doc still applies.
- **Combo: a trapdoor passage keeps the chain.**
  - Today `"seesawPlank"` fires `BallTouchedPlatform` (`ContactDispatcher.java:55-57`), which sets `ScoreManager.touchedSinceLastRow`. So touching a door resets your combo, while falling through still fires `GapPassed` (`manageRows()` decides that by the ball's Y alone).
  - Decision: the plank fires no `BallTouchedPlatform`, so dropping through a door keeps the combo. Landing on the wall filler or the lip still resets as normal.
  - This reverses the old doc's Iron Rule *for this one tag only*, on purpose. The `ContactDispatcherTest` guard flips from "must fire" to "must not fire".
  - **The combo is the only behavior lost.** A grep of `core/src/main/java` shows `ScoreManager` is the only consumer of `BallTouchedPlatform`. There's no audio in the codebase (see TODOS.md), and no haptics, particles or analytics hang off this event. If the audio/SFX pass later adds landing sounds, it needs a separate trapdoor-contact path rather than this event.
- **The door is always an extra way down, never the only one.** The row's guaranteed gap and `GapReachabilityValidator` are untouched. The validator already assumes the ball can be anywhere on 0..WORLD_WIDTH, so a door dropping the ball somewhere unusual can't break reachability. This is the same argument that made WEAK safe.
- **Rampage is still deferred.** The plank is never breakable. The wall filler and lip stay plain `"platform"` (rampage-breakable, per the user's call on the shipped seesaw); a broken lip leaves a working door.

## Premises

1. It REPLACES the shipped flanking seesaw: same `PlatformType.SEESAW` and roll slot, new geometry. The current one adds no decision.
2. It is always an EXTRA way down. The guaranteed gap and reachability math are unchanged.
3. Pure physics: no motor, no scripted velocity. Self-righting comes from a keel below the pivot, with the tilt limit opened to the 70°–85° range (see Symbols and Constraints).
4. No upward or sideways launch. The payoff is choosing to land off-center and dropping through a door you opened.

All four were agreed by the user. The cross-model pass refined the numbers behind Premise 3 (the hole size and the keel bound) but didn't challenge any premise.

## Approaches Considered

### Approach A: Tune by feel (not chosen)
Widen the plank, open the limit to ~75°, add a keel and lips, then tune by playtest. Rejected because the wedge failure and the close-before-the-ball-arrives failure only show up in playtest, which means several device fix cycles.

### Approach B: Prove it, then build (CHOSEN)
- A pure `TrapdoorGeometry` clearance check.
- A headless drop-sweep JUnit test that pins the plank, keel and limit numbers before any `spawnNextRow()` wiring.
- The sweep stays in the suite as a regression guard against later tuning that wedges the ball.

Effort: human ~2 days / CC ~3–4 h. Risk: Low. Accepted downside: the gap-sized hole means doors spawn less often on narrow sides.

### Approach C: Split double doors (not chosen)
Two keeled flaps hinged at each lip, opening downward in the middle like a drawbridge. That allows a ~1.1-unit hatch, which looks distinct and spawns more often. Rejected for this slice: it's about 1.5× the work, with two joints and two keels to tune. It's a natural follow-up if the gap-sized door reads too much like the guaranteed gap.

## Open Questions

- **Exact W, θmax, M, k and angular damping:** pinned by the drop-sweep test (Next Step 2) against the acceptance thresholds defined there, not derived by hand.
- **No static "hold":** with a ball on a level keeled plank there is no stable equilibrium.
  - Any tilt rolls the ball downhill, which tilts the plank further.
  - The ball's center also sits ~0.575 above the pivot, an inverted-pendulum moment that pushes the same way.
  - More keel moment only slows the opening, and the keel bound caps that.

  So a door effectively always swallows a ball that lands on it, unless the player steers against the slope. The sweep **records** the time-to-open from a dead-center, unsteered landing (T_open) for information but does not require a minimum. Whether doors feel too eager is a playtest call. Holding is a steering skill, not a static band.
- **Naming:** keep `PlatformType.SEESAW`/`seesawChance`/`SEESAW_*` (the mechanism is still a center-pivoted seesaw), or rename to `TRAPDOOR`? The tag must change regardless (e.g. `"trapdoorPlank"`) because its combo semantics differ. Lean toward keeping the type names and changing the tag. Eng-review call.
- **Spawn frequency:** a door side needs minFiller + W + minLip = 2.9–3.3 units out of a 5.6–6.6-unit flanking total. Measure the fallback-to-NORMAL rate after wiring, and retune `seesawChance` by feel if doors become rare.
- **Rising door end:** the high end rises about L·sinθmax (~1.2–1.45) above the row while the door is open, and can swat a ball rolling toward the gap. Probably fun, but this is unvalidated geometry. Watch for it in playtest.
- **Deferred:** split double doors (Approach C); vertically stacked "door shafts" in a biome; the rampage interaction (see TODOS.md).

## Success Criteria

- A vertical landing at |x| ≥ 0.4 from the pivot, with no steering or steering toward the low end, opens the door and the ball passes within T_pass = 1.0 s of its last plank contact. Roll-on and steer-against entries pass, bounce out or (steer-against only) hold. **No entry/steering combination ever wedges.** The kept drop-sweep regression test asserts all of this, using the classifications defined in Next Step 2.
- The door settles to level (|θ| < 5°) within 1.5 s of the ball passing, through the keel and angular damping only: no motor, no scripted correction.
- Dropping through a door keeps the combo chain, as long as the ball doesn't graze the wall filler or lip on the way through. The sweep asserts that a no-steer, one-row-drop pass doesn't graze, and records grazes for every other entry. Any graze, and any landing on the filler or lip, still resets the combo. That's accepted, since those are real platform touches.
- The plank never jams against either lip (no-collide group on the plank, wall filler and lip). The keel never collides with anything.
- A flanking span too narrow for wall filler + hole + lip is rejected and rerolled, then falls back to NORMAL, never built broken.
- Row recycling destroys the plank, fulcrum, filler and lip with no dangling joint reference.
- No regression to gap reachability, biomes, moving platforms, weak platforms or rampage.
- The user, playtesting on desktop and the Galaxy A56, picks doors on purpose.

     - A dead-center landing with ±force counts as *toward* for whichever side it tips to.
   - **Classification** (hole span = [pivotX − W/2, pivotX + W/2]). Classes are checked in this order and are mutually exclusive:
     - **passed:** the ball's center goes below `rowY − t/2 − r` while its x is within the hole span.
       - Record the time from the **last** plank contact before passing.
       - Record whether the ball touched the wall filler or lip at any point between first plank contact and passing.
       - Record the peak rebound height above the row.
     - **wedged:** not passed, and over a 0.5 s window the ball's speed stays below 0.2 m/s while it is in simultaneous contact with the plank AND (the wall filler OR the lip). This is defined by stopped descent, not by position, so a wedge below the lip corner still counts.
     - **held:** not passed, the ball's speed is below 0.2 m/s, and the plank is its only contact. **Allowed only in steer-against runs:** that's the legitimate "work the door with your weight" skill. In any other run it fails the test.
     - **bounced out:** not passed, and the ball rests on or leaves across the wall filler or lip outside the hole span.
     - **unclassified:** any run that fits none of the above within 3.0 s of first contact is a test failure.
   - **Acceptance thresholds for the chosen constants:**
     - zero **wedged** and zero **unclassified** runs in any entry/steering combination;
     - **vertical landings at |x| ≥ 0.4, no-steer or steer-toward:**
       - must **pass**, within T_pass = 1.0 s of the last plank contact (measured from the last contact so a high rebound that lands back on the door isn't penalized);

     - **steer-against runs:** pass, bounce out or held, never wedge;

     - T_open (dead-center, no steering) and rebound heights are recorded, not asserted;
     - expected-fail control cells must classify as not-passed.

     1. smallest W (spawns more often);
     2. smallest θmax (lower rising end);
     3. largest T_open (least eager door);
     4. fastest settle;

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: MAX_ITERATIONS

### R3-1 — feasibility

**Problem**

> The expected-fail control cells would physically pass the ball, so the assertion that they 'must classify as not-passed' would fail. The controls are W = 2.3 with θmax 70°, 75° and 80°. Using the document's own clearance formula (W/2)·sinθ − 0.175·cosθ − 0.175, a 2.3 hole gives about 0.846 at 70°, 0.890 at 75° and 0.927 at 80°. All three exceed the 0.8 ball diameter, and the 80° cell even exceeds the 0.9 margin target. The θ_pass + 5° rule is a design safety margin, not a physical limit, so these cells are not too-small holes.

**Remedy**

> Use controls whose clearance at θmax is below d_ball = 0.8. For example, W = 2.0 at 70° gives about 0.705, and the shipped W ≈ 1.6 also works. Alternatively, drop the 'must classify as not-passed' assertion and treat the θ_pass + 5° rule only as a filter that excludes cells from selection.

### R3-2 — feasibility

**Problem**

> In a deterministic simulation, the dead-center (x = 0), no-steer landing may never tip. A symmetric ball landing exactly on the pivot of a symmetric keeled plank has no asymmetric force to break the unstable equilibrium, and floating-point error may not supply one. The ball would then be 'held' in a no-steer run, which the classification defines as a test failure. T_open would also be undefined, and T_open is the third key of the selection rule. This contradicts the Open Questions claim that a door 'effectively always swallows a ball'.

**Remedy**

> State the expected outcome for x = 0 no-steer runs: allow 'held' there, or add a defined tiny perturbation such as a fixed offset like 0.01. Define T_open for a run that never opens (for example, cap it at the run length), and say how the selection rule ranks such a value.

### R3-3 — consistency

**Problem**

> Measuring T_pass from the last plank contact makes the gate nearly vacuous. For any pass, the ball's last plank contact comes moments before it drops below rowY − t/2 − r, so almost any pass meets 1.0 s. A sluggish door that carries the ball for 2.5 s before opening satisfies T_pass, and only the 3.0 s unclassified cap still limits it. Yet the Success Criterion says an off-center landing 'opens the door and the ball passes within T_pass', which implies a promptness guarantee the test no longer enforces.

**Remedy**

> Measure T_pass from the start of the final landing, meaning the first plank contact after the ball's last airborne phase, so rebounds still aren't penalized. Or add a separate bound on time from first contact to pass for vertical landings at |x| ≥ 0.4. Then make the Success Criteria wording match.

### R3-4 — clarity

**Problem**

> Classification timing is undefined. 'Wedged' uses a 0.5 s window, but 'held' is a single moment: speed below 0.2 with the plank as the only contact. The design doesn't say whether classes are evaluated continuously or once at the end of the run. A ball that slows briefly on a tipping door in a no-steer run could therefore count as held, which fails the test, even if it passes a moment later. 'First contact', which starts the 3.0 s unclassified cap, is ambiguous for roll-on entries, where the ball starts on the filler or lip. Run length is also unstated: a pass near 3.0 s needs another 1.5 s to check the settle criterion.

**Remedy**

> Say when classification happens. For example: 'passed' may occur at any time; otherwise classify from the final state, with held requiring a sustained window like wedged. Define first contact as the first plank contact for every entry type. Set the run length to cover the 3.0 s cap plus the 1.5 s settle check.

### R3-5 — clarity

**Problem**

> 'Wedged' has no position qualifier, and it is checked before 'bounced out'. So a ball at rest on the lip or filler that also touches the plank counts as wedged even though it is outside the hole. Two cases cause this: the ball sits over the 0.1 region where the plank overlaps a lip, or the ball rests against the raised high end of an open door, the 'rising door end' case. Whether either case is a true failure or a bounce-out is undecided, and that choice can decide whether a parameter set passes the zero-wedged gate.

**Remedy**

> Decide whether a stalled ball outside the hole span that touches the plank counts as wedged. Restrict 'wedged' to ball positions within or below the hole span, or explicitly keep these cases as wedges. Then state the decision.

### R3-6 — completeness

**Problem**

> The sweep's test world never specifies the filler and lip widths, whether walls and the guaranteed gap are present, or where roll-on entries start. These choices affect the outcomes the sweep measures. minFiller = 0.3 is narrower than the ball's radius of 0.4, so a ball can't roll onto the door from a minimum-width filler without starting against the wall. Contact with the filler and lip also decides the wedge, bounce-out and graze results.

**Remedy**

> Specify the test-row layout: the span width(s), the filler and lip widths (including the minimum-span case that ships), whether there's a wall body, and the start position for each roll-on entry. If the shipped geometry differs, say whether the sweep covers both the minimum and a typical span.

### R3-7 — consistency

**Problem**

> The restitution adoption rule contradicts the selection rule. The adoption rule says the preSolve override 'ships only if no as-is combination meets every acceptance threshold'. But the selection rule ranks smallest W and smallest θmax first and puts 'as-is restitution over the override' last. That ranking would pick an override combination with a smaller W even when as-is combinations also pass.

**Remedy**

> Make restitution the first filter in the selection rule: use as-is combinations if any pass, otherwise the override. Or rewrite the adoption rule to match the current ordering.

### R3-8 — consistency

**Problem**

> The document doesn't settle whether the full sweep runs in the normal suite. Approach B says 'the sweep stays in the suite as a regression guard', but Next Step 2 says to keep only 'a focused version as the regression guard'. The full grid is large: 3 W × 4 θmax × 3 M × 3 k × 3 damping × 2 restitution = 648 cells before skips. Each cell runs about 37 entries × 3 steering cases, roughly 111 runs of up to about 4.5 s simulated. That totals about 70k runs and tens of millions of world steps. Nothing says how the full sweep is run, kept out of the default `test` task, or where its results table is recorded.

**Remedy**

> State that only the focused chosen-constants test runs in the normal suite. Say how the full sweep is invoked (for example, a tagged or excluded JUnit class or a system property), and where its table is written so the chosen constants can be traced.
